개인모드 챗봇 로직

회원 한 명을 위한 온보딩 → ACSM 안전 스크리닝 → 다중 세션 주기화 → 채팅 기반 세션 생성/피드백/잡담 라우팅까지, 개인모드 챗봇 "그로우디"의 전체 파이프라인을 처음부터 끝까지 설명합니다. 이 문서만 읽어도 코드를 열어보지 않고 흐름을 이해할 수 있도록 만들었습니다.

세션 생성 엔트리포인트 generate_personal_session(request_body) -> dict 채팅 엔트리포인트 chat_reply() / run_chat() 페르소나 🩵 그로우디

00 한눈에 보기

3개 파일이 계층을 이룹니다. 아래로 갈수록 "팀 모드에 없는" 개인 전용 로직이 얹힙니다. 주의: 이 계층은 teamprogram_ver1.generate_curriculum()을 호출하는 구조가 아닙니다 — 그 안에 정의된 공통 표·함수(카테고리/존 로직)만 라이브러리처럼 가져다 쓰고, 완전히 독립된 개인 전용 엔트리포인트(generate_personal_session())를 씁니다.

아직 프로토타입입니다: personal_chat_ver1.py는 현재 FastAPI 백엔드(apps/server/app/api)에 연결되지 않은 CLI·로컬 개발서버 전용 코드입니다. 저장소 전체에서 이 모듈을 참조하는 곳은 자기 자신과 run_personal_ver1.py, personal_chat_dev_server.py류 테스트/개발 도구뿐입니다.

01 온보딩 폼 스키마

온보딩은 진입 시 1회, 구조화된 폼(단계별 위저드)으로만 수집합니다 — 통증·질환 여부 같은 안전 데이터를 대화체 자유 텍스트에서 파싱하면 오분류 위험이 안전 문제로 직결되기 때문입니다. (personal_onboarding_form.md)

섹션대표 필드용도
A. 기록·피트니스pb_50m{free/back/breast/fly}, css_pace_sec_per_100m, weekly_frequency레벨 추정(_infer_level), 개인 강도 계산 기준 페이스
B. 목표goal_type, target_event_date카테고리 선정, 주기화(taper) 판정
C. 신체·안전 (ACSM)activity_level, has_symptoms_or_disease, desired_intensityscreen()의 3요소 그대로
D. 환경·제약pool_length_m, session_duration_min, equipment목표 운동량·구간 시간 계산
E. 주관 캘리브레이션rpe_calibration (CR-10, 0~10)페이스 기록 없을 때 RPE 기반 지도 기준
★ stroke_primary(주 영법)는 온보딩에서 받지 않습니다. 영법은 세션마다 달라질 수 있는 정보라서, 매 세션 생성 요청 시점에 채팅 슬롯 채우기로 물어봅니다. pb_50m도 마찬가지로 "특정 영법 하나"가 아니라 4영법 50m 기록을 한 번에 구조로 받도록 바뀌었습니다(과거 pb_record/stroke_primary 단일값 방식에서 교체).

02 ACSM 사전 스크리닝

screen(activity_level, has_symptoms_or_disease, desired_intensity)는 ACSM 최신 모델의 3요소만 봅니다. 온보딩 1회 + "마이페이지"에서 C 섹션을 수정한 직후(다음 세션 생성 요청 시점)에만 재실행되며, 매 세션마다 다시 하지 않습니다.

REFER_TO_PHYSICIAN이면 generate_personal_session()은 {"referral": true, "message": "..."}만 반환하고 LLM 호출 자체를 하지 않습니다 — 비용도, 위험도 둘 다 사전 차단.

03 개인 세션 생성 파이프라인

personar_ver1.generate_personal_session(request_body) -> dict — 팀 모드의 generate_curriculum()과 대응하는 개인 전용 엔트리포인트입니다.

1

ACSM 스크리닝

screen() 결과가 REFER면 즉시 반환(§2).

2

레벨·나이대 추정

_infer_level(profile) — pb_50m 중 하나라도 값이 있거나 css_pace_sec_per_100m가 있으면 "기록 있음", 여기에 weekly_frequency를 더해 BEGINNER~MASTER 5단계로 근사. profile.level이 직접 있으면 그 값이 항상 우선.

3

카테고리 선정 + 주기화 + 피드백 반영

팀 모드와 같은 select_categories()로 1차 선정 → apply_periodization()이 디로드/taper를 반영해 카테고리를 조정 → apply_feedback_adjustment()이 직전 체감 RPE로 존을 한 단계 낮출지 결정.

4

개인 강도 계산

calc_personal_intensity() — CSS(역치) 페이스가 있으면 ZONE_PCT_OF_THRESHOLD 표로 존별 목표 페이스(초)를 스케일링, 없으면 RPE 목표치만 반환(RPE 기반 지도로 전환).

5

드릴 풀 · 인터벌 지시 구성

팀 모드와 동일한 사전 차단 철학 — Pre/Post는 intensity=='low'만, Main-Set은 content_type에 따라 드릴 또는 build_interval_set().

6

이론 자료 검색 & LLM 호출

pdf_db.similarity_search(k=8)(임계값 필터 없음) → personal_prompt_template로 LLM 호출 → JSON 파싱(실패 시 1회 재시도, 팀 모드와 동일 패턴).

7

후처리 & 반환

총 거리/시간 서버 재계산, plan_context.category/zone을 이번에 실제 쓰인 값으로 덮어씀(다음 세션의 주기화 계산이 이 값을 session_history로 이어받음), feedback_request 기본값 채움.

출력 스키마 — 팀 모드와 다름(자유 설계)

{
  "plan_context": { "phase": "EN_BASE", "category": "B", "zone": "EN2",
                     "note": "이번 세션이 전체 계획에서 어떤 위치인지" },
  "session_summary": { "focus_point": "...", "total_distance_m": 1400, "total_min": 60 },
  "program": {
    "main_set": [ { "title": "...", "set": 8, "distance_m": 100, "duration_min": 24,
                    "target_pace_sec": 112, "rpe_target": 6, "detail": "...", "effect": "..." } ]
  },
  "next_session_hint": "다음 세션 방향 한 문장",
  "feedback_request": ["오늘 세션 완료했나요?", "체감 강도는 몇 점이었나요(0-10)?"]
}

팀 모드 필드명(title/set/distance_m/duration_min/detail)은 유지하되, target_pace_sec·rpe_target·effect·plan_context·next_session_hint·feedback_request를 자유롭게 추가합니다 — 팀 모드와 달리 개인 모드는 출력 계약이 고정돼 있지 않습니다.

04 다중 세션 주기화 · 피드백 루프 팀 모드에 없는 기능

단발 세션이 아니라 여러 세션에 걸친 흐름을 관리하는, 개인 모드만의 핵심 기능입니다.

규칙값동작
디로드(회복) 세션4회마다len(session_history) % 4 == 3이면 이번 세션 강도를 2단계 낮춤(_step_zone(..., -2))
대회 임박 taperD-14 이내target_event_date까지 0~14일 남았으면 카테고리를 E(레이스 준비)로 전환 추천
체감 강도 하향 조정RPE +2 이상rpe_actual이 계획 중앙값보다 2 이상 높았으면 다음 세션 존을 1단계 낮춤 — 낮거나 비슷하면 계획대로 진행(자동 상향은 없음)
세션 간 상승 제한팀 모드와 동일이전 세션 대비 1단계 이상 연속 상승 금지 — get_zone_params(previous_session=...)가 그대로 적용

피드백 루프: 세션 종료 후 feedback_request에 대한 답(완료 여부·체감 RPE)이 다음 GENERATE_SESSION 요청의 last_feedback으로 들어가 위 "체감 강도 하향 조정" 규칙에 쓰입니다.

05 채팅 오케스트레이션

generate_personal_session()은 "요청 dict → 응답 dict" 단발 함수라 여러 턴에 걸친 자유 대화(문맥 유지, 잡담 응답)는 못 합니다. personal_chat_ver1.py는 그 위에 매 턴 "일반 대화 / 세션 생성 요청 / 세션 후 피드백"을 판단해 라우팅하는 얇은 레이어입니다.

classify_intent(user_message, recent_history) -> str가 매 턴 세 갈래로 분류합니다. 분류 자체가 실패하면(LLM 오류 등) 항상 CHAT으로 안전하게 폴백합니다 — 잘못 판단해 세션을 함부로 만들지 않기 위해서입니다.

intent트리거 예시처리
GENERATE_SESSION"오늘 훈련 만들어줘"슬롯 채우기 → generate_personal_session() 호출
FEEDBACK"오늘 다 했어요, 좀 힘들었어요"extract_feedback()로 완료여부/RPE 추출 → last_feedback에 저장(세션 생성은 안 함)
CHAT"오늘 컨디션이 좀 별로예요"RAG 그라운딩 잡담 응답

06 세션 생성 전 슬롯 채우기

stroke_primary가 온보딩에서 빠지면서, 영법처럼 세션마다 달라질 수 있는 정보는 매 GENERATE_SESSION 요청 시점에 채팅으로 확인합니다. 회원이 메시지에 이미 답을 해뒀으면 다시 묻지 않습니다.

슬롯라벨선택지
stroke영법자유형 / 배영 / 평영 / 접영 / 상관없음
focus오늘 세션 초점지구력 늘리기 / 스피드 올리기 / 자세 교정 / 가볍게
condition오늘 컨디션평소와 같음 / 좀 피곤함(강도 낮춰줘) / 특정 부위 불편함

find_missing_slots()가 메시지+최근 대화에서 이미 채워진 슬롯을 판별합니다. 판별 자체가 실패하면 "3개 다 못 채움"으로 안전하게 처리합니다(한 번 더 묻는 게, 안 묻고 넘어가는 것보다 안전).

07 잡담용 RAG 그라운딩

세션 생성 요청은 항상 기술적 맥락이 있어 generate_personal_session()이 매번 이론 자료를 검색하지만, 잡담 한 줄("오늘 컨디션 어때요")은 이론서에 대응 내용이 없는 게 정상이라 매 턴 벡터 검색을 하면 비용만 붙습니다. 그래서 2단계 필터를 씁니다.

키워드 소스내용
_SWIM_KEYWORDSdrill_picker.STROKE_DETECT + SKILL_DETECT 재사용(영법명, 턴/스타트/피니시 등)
_CHAT_EXTRA_KEYWORDS 이번 세션 신규일반 수영 용어(수영/수영장/레인 등), 장비, 신체 통증(어깨/허리/무릎/통증/아파요 등 — 기존엔 전혀 없었음), 훈련·기록 용어, 캐주얼한 체력·호흡 표현(숨차/지쳐 등)
FOCUS_TERMSdrill_picker의 한글 코칭 키워드(자세/교정/발차기/호흡 등)를 원문 그대로 재사용
RAG_RELEVANCE_THRESHOLD = 0.5는 아직 완전히 검증된 값이 아닙니다. calibrate_rag_threshold.py(§10)로 실측한 결과 평영 질문 기준 0.67~0.69점이 통과하는 것은 확인했지만, 케이스 수가 많지 않아 추가 보정 여지가 있습니다.

페르소나: chat_reply()는 chat_llm(JSON 강제 없음, temperature 0.5 — 세션 생성용 LLM과 별개 인스턴스)을 호출하며, 시스템 메시지에 🩵 "당신은 친절한 수영 개인 코치 챗봇 그로우디입니다"가 고정으로 들어갑니다. 프로필 중 goal_type/age만 참고하고(stroke_primary는 더 이상 참조하지 않음), 최근 대화 6턴만 잘라서 넘깁니다.

08 대화 루프 상태 머신 — run_chat()

슬롯 질문에 대한 답은 별도 의도 분류 없이 처리해야 하므로, 루프는 pending_session_request 상태 변수로 "직전 턴에 슬롯을 되물었는지"를 기억합니다.

알려진 단순화: 슬롯 답변 병합 후에는 answer["missing"]이 아직 남아 있어도 재확인 없이 바로 세션 생성으로 진행합니다 — 슬롯을 여러 라운드에 걸쳐 되묻는 로직은 없습니다(최대 1라운드).
