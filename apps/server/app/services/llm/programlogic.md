## 0. 이 문서의 구조

1. **공통 코어** — 팀/개인이 함께 쓰는 지식·계산 레이어. 훈련지도서 8존 분류를 생활체육에 맞게 재해석.
2. **팀 설계(현재 프로그램)** — 내부 로직은 공통 코어로 교체하되, **출력 스키마는 100% 동일하게 유지**.
3. **개인 설계(신규)** — 챗봇 기반, ACSM 스크리닝 포함, 입력·출력 모두 신규 정의.

## 1. 공통 코어 — 훈련 분류 체계

### 1-1. 원본(훈련지도서 표 5-1)과 생활체육 적용의 차이

원본 8존(Recovery/A1, EN1, EN2, EN3, SP1, SP2, SP3 + 레이스페이스)은 국가대표급 선수의 **개인 최고기록(PB)** 이 있다는 전제로 심박수·%AT·젖산농도·페이스를 계산합니다. 생활체육 회원·강사는 이 데이터가 없으므로 그대로 못 씁니다.

**가져오는 것:** 존 구분 자체, 휴식:운동 비율, 반복 패턴의 "형태", 그리고 표에 이미 있는 **주관적 운동강도(RPE)** 문구.
**버리는 것:** %AT 수치, 심박수 절대값, 젖산농도(mM), 절대 반복 거리(예: "3,000m 이상"은 선수 기준).
**대체하는 것:** 절대 거리량은 기존 `calc_target_distance()`(판교 진도표·마스터즈 실측 기반)로 계산한 값을 그대로 쓰고, 그 예산 안에서 존별 반복 패턴 형태만 적용합니다.

### 1-2. 카테고리(강사·사용자에게 노출되는 상위 분류, 5개)

| 카테고리 | 내부 매핑 존 | 콘텐츠 타입 | 비고 |
|---|---|---|---|
| A. 놀이·물적응 | (신규, 훈련지도서 밖) | 드릴 라이브러리 전용 | 원본에 근거 없음. 별도 자료 필요 (PROGRAM_LOGIC.md 기존 지적과 동일) |
| B. 지구력 | Recovery/A1 · EN1 · EN2 · EN3 | EN1까지는 드릴+이지스윔 혼합 / EN2 이상은 인터벌 세트 직접 생성 | |
| C. 스피드·파워 | SP1 · SP2 · SP3 | 인터벌 세트 직접 생성 (드릴 아님) | 고강도 — 레벨 게이팅 필수 |
| D. 기술·교정 | (존 무관, 기존 방식) | 드릴 라이브러리 전용 | 지금 `drill_picker.py`가 하던 일 그대로 |
| E. 레이스 준비 | 레이스 페이스 트레이닝(표 5-14·15) | 인터벌 세트 직접 생성 | MASTER 전용 옵션 |

★ 카테고리 선택은 "1-2가지"까지 허용(예: B+D 조합, C+D 조합). LLM에게 완전 자유 위임하지 않고, 레벨이 카테고리 후보를 먼저 좁힌 뒤 강사/사용자가 그 안에서 고르는 구조를 권장합니다.

### 1-3. 콘텐츠 타입 분기 — 구간(phase) 기준이지, 카테고리 기준이 아님

기존 `drill_library.json` 200개는 전부 **기술 교정용 드릴**(Name/Purpose/How 형식)입니다. EN2 이상·SP1~3은 기술 드릴이 아니라 **정해진 거리·반복·휴식으로 수영하는 인터벌 세트**입니다. 이 둘을 같은 파이프라인에서 섞으면 안 됩니다.

**중요(수정): 이 분기는 "이번 세션에 어떤 카테고리를 골랐는가"가 아니라 "지금 채우는 게 pre_set·main_set·post_set 중 어디인가"로 결정합니다.** 카테고리 C(스피드·파워)를 고른 세션이라도 pre_set·post_set까지 인터벌 세트로 채우면 안 됩니다 — 오히려 본 운동 강도가 높을수록 준비·정리운동은 더 확실하게 저강도 드릴이어야 합니다.

| 구간 | 콘텐츠 소스 |
|---|---|
| pre_set (항상, 메인 카테고리 무관) | Recovery/A1·EN1 존의 드릴만 — `drill_picker.py` 조회 |
| post_set (항상, 메인 카테고리 무관) | Recovery/A1·EN1 존의 드릴만 — `drill_picker.py` 조회 |
| main_set — 카테고리 A/D, 또는 B의 Recovery·EN1 | `drill_picker.py` → `drill_library.json` 조회 (기존 방식 유지) |
| main_set — 카테고리 B의 EN2·EN3, 카테고리 C, 카테고리 E | 드릴 조회 없이 §1-4 구조 파라미터로 인터벌 세트를 직접 계산·생성 |

### 1-4. 존별 구조 파라미터 (RPE 기반, 생활체육용으로 치환)

| 존 | 목적 | RPE(CR-10 환산) | 휴식:운동 | 반복 단위 가이드 | 콘텐츠 | 적용 가능 구간 |
|---|---|---|---|---|---|---|
| Recovery/A1 | 회복·이완 | 2~3 (매우 가볍다) | 자유 | 연속 이지스윔 | 드릴/이지스윔 | pre·main·post 전부 |
| EN1 | 기초 지구력 | 3~4 (가볍다) | 10~30초 | 25~50m 단위, 다회 반복 | 드릴+이지스윔 | pre·main·post 전부 |
| EN2 | 역치 지구력 | 5~6 (약간 힘들다) | 10~30초 | 50~100m 단위 | 인터벌 세트 | main만 |
| EN3 | 과부하 지구력 | 7 (힘들다) | 20초 또는 1:1 | 100~200m 단위 | 인터벌 세트 | main만 |
| SP1 | 젖산 내성 | 8~9 (매우 힘들다) | 1:1~1:2 | 50~100m 단위 | 인터벌 세트 | main만 |
| SP2 | 젖산 생성 | 9 (매우 힘들다) | 1:2~1:3 | 25~50m 단위 | 인터벌 세트 | main만 |
| SP3 | 파워 | 9~10 (최대) | 1:2~1:6 | 12.5~25m 단위 | 인터벌 세트 | main만 |
| 레이스 페이스 | 대회 시뮬레이션 | 목표 페이스 기준 | 세트 간 2~3분 | 출전 종목 거리 기준 | 인터벌 세트 | main만 |

**Recovery/A1·EN1만 "pre·main·post 전부"인 이유가 곧 §1-3 규칙의 근거입니다.** EN2 이상은 표에 애초에 main만 표시돼 있으므로, pre_set·post_set 후보 자체가 Recovery/A1·EN1로 자동 제한됩니다.

출처: 훈련지도서 표 5-2~5-15의 훈련강도·휴식비율·반복 패턴 열. 절대 반복수·거리는 옮기지 않고, **총량은 §1-5의 기존 계산값을 그대로 쓰고 이 표는 "그 안에서 어떻게 나눠 담을지"의 비율/패턴만 제공**합니다.

★ RPE를 CR-10(0~10)으로 통일한 것은 이 문서의 제안입니다. 원문은 6~7, 7~8 같은 표현이라 Borg 6-20 스케일에 가깝지만, 소비자 대상 챗봇·강사 UI에는 0~10이 더 직관적이라 판단했습니다 — 강사 검수 필요.

### 1-5. 레벨 × 카테고리 게이팅

| level | 허용 카테고리 |
|---|---|
| PRESCHOOL(연령) | A만 |
| BEGINNER(신규) | A, D, B(Recovery~EN1) |
| ELEMENTARY(초급) | D 중심 + B(EN1) |
| INTERMEDIATE(중급) | D + B(EN1~EN2) |
| ADVANCED(상급) | D + B(EN1~EN3) + C(SP1) |
| MASTER(마스터) | 전체(B/C/D/E, EN1~EN3, SP1~SP3) |

SP1~3과 레이스 페이스는 팀 모드에서 ADVANCED 이상으로 제한합니다(근거: HANDOFF §12 F-2와 같은 성격의 안전 이슈 — 검증되지 않은 회원 집단에 고강도를 자동 배치하면 안 됨). 개인 모드는 §3-3 ACSM 스크리닝 결과로 별도 게이팅합니다.

### 1-6. 공통 계산 함수 스펙 (기존 `rag_service_ver4.py` 확장)

기존 함수는 이름·시그니처 유지, 아래 함수를 신규 추가:

```
select_categories(level, age_group, goal_text, request_text) -> [category, ...]
  # §1-5 게이팅 매트릭스로 후보 좁힌 뒤, goal/request 키워드로 1-2개 선정.
  # 강사가 명시적으로 요청한 게 있으면(예: "지구력 위주로") 그것을 우선.

get_zone_params(category, level, phase) -> {rpe, rest_ratio, rep_unit_range, content_type}
  # §1-4 표 조회. phase가 pre_set·post_set이면 무조건 Recovery/A1·EN1로 강제 치환
  # (선택된 category가 무엇이든 무시) → content_type은 항상 'drill'.
  # phase가 main_set이면 선택된 category/zone 그대로 조회 → content_type이
  # 'drill'이면 기존 drill_picker 경로, 'interval_set'이면 build_interval_set() 경로.

build_interval_set(zone_params, target_distance_budget, duration_budget, stroke) -> [set_item, ...]
  # main_set에서만 호출됨(§1-3). pre_set·post_set은 애초에 이 함수를 호출하지 않음.
  # target_distance_budget: 기존 calc_target_distance()가 이미 계산한 값(카테고리 배분 후 일부).
  # 존의 rest_ratio·rep_unit_range로 세트 수·거리·휴식을 나눠 담음. 드릴 조회 없음.
```

`calc_target_distance()` · `calc_phase_minutes()` · `LEVEL_RATE` · `AGE_MULTIPLIER` · `EQUIP_MULTIPLIER`는 그대로 둡니다 — 이미 실측 근거가 있는 부분이라 교체 대상이 아닙니다.

## 2. 팀 설계 (현재 프로그램) — 출력 계약 고정

### 2-1. 출력 스키마 — 변경 금지 (그대로 명시)

`rag_service_ver4.py`의 현재 계약을 그대로 고정합니다. 프론트엔드는 이 스키마만 보고 동작하므로, 내부 로직이 §1의 공통 코어로 바뀌어도 아래 구조·필드명·타입은 절대 바뀌지 않습니다.

```json
{
  "session_summary": {
    "focus_point": "string, 100자 이내",
    "total_distance_m": "int (서버 합산값)",
    "total_min": "int (서버 합산값)"
  },
  "program": {
    "pre_set":  [{"title": "string", "set": "int", "distance_m": "int", "duration_min": "int", "detail": "string, 80자 이내"}],
    "main_set": [{"title": "string", "set": "int", "distance_m": "int", "duration_min": "int", "detail": "string, 80자 이내"}],
    "post_set": [{"title": "string", "set": "int", "distance_m": "int", "duration_min": "int", "detail": "string, 80자 이내"}]
  }
}
```

**필드 추가·이름 변경·타입 변경 전부 금지.** `detail` 필드를 더 자세하게 쓰는 것(§2-6)은 이 필드 안에서 문장 품질을 올리는 것이지 스키마 변경이 아니므로 허용됩니다.

### 2-2. 입력 스키마 — 기존과 동일, 신규 optional 필드만 추가

기존 `RequestBody`(level/age_group/duration_min/capacity/goal/goal_etc/equipment/request)는 그대로 유지합니다. 아래 필드는 **optional**로 추가 — 없어도 기존과 동일하게 동작해야 합니다.

```json
{
  "...기존 필드 전부 동일...": "...",
  "previous_session": {          // optional, §2-5
    "category": "B",
    "zone": "EN1",
    "total_distance_m": 900,
    "main_drills": ["캐치업 드릴", "스트림라인 킥"]
  }
}
```

### 2-3. 파이프라인 변경사항 (이전 대화 정리)

1. `select_categories()` — 레벨·나이대·goal/request로 카테고리 1-2개 결정 (§1-6)
2. `get_zone_params()` — 카테고리별 존 파라미터 조회, 콘텐츠 타입 분기
3. 목표 운동량·구간 시간 계산 (기존 `calc_target_distance()`/`calc_phase_minutes()` 그대로)
4. 콘텐츠 채우기: drill 타입 → 기존 `drill_picker.pick_drills()` / interval_set 타입 → `build_interval_set()`
5. 부족한 코칭 근거만 `pdf_db` 벡터 검색으로 보강 (기존 방식 유지, 있으면 포함 없으면 스킵 — 이미 그렇게 동작 중)
6. LLM 호출 — 프롬프트에 "존 목적·RPE·구조"를 명시적으로 주입해 세트 구성 근거를 부여
7. JSON 파싱 (기존 재시도 로직 유지)
8. 목표 재조정 (기존 `_adjusted_targets()` 로직 유지)
9. 검증·재생성 (기존 로직 유지, §1-5 게이팅 위반 시 재생성 사유 추가: "고강도 카테고리가 레벨 게이팅을 벗어남")

### 2-4. 안전 게이팅 — 코드 레벨 강제로 승격

현재 F-2(쿨다운 고강도 드릴)는 "로그 경고만" 상태입니다. §1-3·§1-4의 구간별 콘텐츠 규칙이 도입되면서 이건 경고가 아니라 **애초에 후보가 안 생기는 구조**로 바뀝니다.

- pre_set·post_set은 `get_zone_params(phase=pre_set/post_set)`이 항상 Recovery/A1·EN1만 반환하므로, 메인 카테고리가 무엇이든 LLM에게 고강도 드릴 자체가 후보로 보이지 않습니다(§1-3). 로그 경고로 사후 탐지하던 방식에서 사전 차단으로 바뀝니다.
- SP1~3·레이스페이스는 §1-5에서 허용 안 된 레벨이면 `select_categories()` 단계에서 후보에서 제외 — LLM에게 애초에 보여주지 않음.

### 2-5. 이전 수업 참고 (신규, optional 입력)

`previous_session`이 있으면 프롬프트에 "지난 세션 카테고리/존/주요 드릴"을 참고 정보로 제공하고, **강도 상승은 한 단계까지만** 허용하는 규칙을 프롬프트 제약으로 명시(예: 지난주 EN1 → 이번주 EN2까지는 가능, EN3로 바로 못 감). 이 필드가 없으면 기존과 완전히 동일하게 동작 — 출력 계약에 영향 없음.

### 2-6. 코칭팁 확장 — 스키마 안 지키면서 품질만 올리기

`detail` 필드(80자, 1문장)는 그대로 두고, 프롬프트에서 근거 우선순위를 명확히 합니다: ① 존의 "목적" 문구(§1-4) ② 드릴의 `purpose_text`(이미 `drill_library.json`에 있는데 지금 프롬프트에 안 넘기고 있음 — 이것만 추가로 넘겨도 LLM이 즉흥으로 안 지어내고 원문 근거를 씀) ③ `pdf_db` 이론 검색 결과. 필드를 늘리는 안(예: `effect` 필드 분리)은 스키마 변경이라 **팀 모드에서는 보류**, 필요해지면 별도 버전 협의 후 프론트와 동시 반영합니다.

## 3. 개인 설계 (신규)

### 3-1. 상호작용 모델 (수정: 개발 공수 고려한 1차 범위)

팀 모드는 폼 1회 제출 → 세션 1개 생성입니다. 개인 모드는 아래 세 화면/기능으로 나눕니다 — **개인정보 수집은 진입 시점 1회로 한정하고, 그 이후 상호작용은 순수 채팅만** 둡니다.

1. **온보딩(최초 진입 1회)**: §3-2 입력을 **구조화된 폼(단계별 위저드)**으로 수집합니다. 대화체 챗봇이 순차 질문하며 파싱하는 방식은 채택하지 않습니다 — PB·날짜·ACSM 예/아니오 같은 안전·수치 데이터를 자유 텍스트에서 파싱하면 오류 위험이 크고(예: 통증 여부를 잘못 파싱하면 안전 문제로 직결) 개발 공수도 더 듭니다. ACSM 스크리닝(§3-3)을 통과해야 프로필이 저장되고 세션 생성이 열립니다.
2. **세션 생성/채팅(반복)**: 순수 채팅. "오늘 훈련 만들어줘" 같은 요청과 세션 후 피드백(§3-7)만 여기서 처리합니다. 채팅은 매 응답마다 프로필을 새로 읽습니다(캐시하지 않음) — 마이페이지에서 방금 수정한 값이 다음 응답부터 바로 반영되어야 하기 때문입니다.
3. **마이페이지**: 프로필(개인정보, PB, 목표, 제약조건) 조회·수정 + 진행한 훈련(세션 히스토리) 조회. 채팅 로그 자체를 저장·재구성하지 않고, **프로필과 프로그램(세션) 기록 두 가지만 영속 저장**합니다 — 상태의 원천을 채팅 텍스트가 아니라 구조화된 두 테이블로 고정하면, 다음 세션 생성 로직이 매번 채팅 이력을 다시 해석할 필요가 없어 안정적입니다.

**주의**: 마이페이지에서 §3-2C(신체·안전) 항목을 수정하면, 그 즉시가 아니라 **다음 세션 생성 요청 시점에 `screen()`을 자동 재실행**합니다(§3-3). 신체 상태 변경이 조용히 반영만 되고 재스크리닝을 안 거치면 안전 게이팅이 무력화됩니다.

### 3-2. 입력 데이터 스펙

**A. 기록/피트니스**
- 주 영법 및 최근 기록(PB) — 있으면 직접 입력, 없으면 CSS 테스트 유도(200m+400m 타임 트라이얼 2회 → 역치 페이스 추정)
- 최근 훈련 빈도(주당 횟수), 평균 세션 거리

**B. 목표**
- 목표 유형(체력/기록단축/대회준비/자세교정/재활 등)
- 목표 대회 있으면: 날짜, 종목, 목표 기록

**C. 신체/안전 (ACSM 스크리닝, §3-3)**
- 나이, 현재 신체활동 수준(비활동적/규칙적)
- 심혈관·대사·신장 질환 관련 증상 또는 진단 여부
- 부상 이력/현재 통증 부위, 임신 여부

**D. 환경/제약**
- 레인 길이(25m/50m), 주당 가능 횟수·요일, 세션당 가능 시간
- 개인 장비, 실내외, 파트너 유무

**E. 주관 캘리브레이션**
- 온보딩 RPE 캘리브레이션(예: "가장 최근 힘들었던 수영이 10점 중 몇 점이었나요")

### 3-3. ACSM 사전 스크리닝 로직

ACSM 최신 모델은 3요소로 운동 전 의료 상담 필요 여부를 판단합니다(위험군을 미리 등급화하던 구모델 대신, 아래 3가지만 봅니다):

1. 현재 신체활동 수준(규칙적 운동 여부)
2. 심혈관·대사·신장 질환의 징후/증상 또는 기존 진단 여부
3. 원하는 운동 강도(경도~중강도 vs 고강도)

```
screen(activity_level, has_symptoms_or_disease, desired_intensity) -> "PROCEED" | "REFER_TO_PHYSICIAN"
  # has_symptoms_or_disease가 True면 강도 무관하게 REFER.
  # 비활동적 + 고강도 희망이면 REFER (또는 저강도부터 시작 권고로 전환).
  # 그 외는 PROCEED.
```

`REFER_TO_PHYSICIAN`이면 세션 생성 자체를 진행하지 않고 전문의 상담 안내만 출력합니다 — 이 판단은 매 세션마다 다시 하지 않고, 온보딩 1회 + 마이페이지에서 §3-2C 항목을 수정한 직후(다음 세션 생성 전) 재실행합니다(§3-1 참고).

### 3-4. 개인 강도 계산

- **페이스 기반 (기록 있는 경우)**: CSS 또는 PB로 역치 페이스 산출 → §1-4 존 표의 %는 버리고 구조(반복/휴식)만 적용하되, 개인은 실측 페이스가 있으므로 팀 모드와 달리 EN2 이상 인터벌 세트에 **실제 목표 페이스(초)** 를 계산해 넣을 수 있습니다.
- **HRR/Karvonen (심박 데이터 있는 경우, 옵션)**: 목표 심박 = (최대심박 − 안정심박) × 강도% + 안정심박. 웨어러블 연동 전제라 1차 범위 아님 — 입력 필드만 만들어두고 연동은 이후 단계.
- **RPE 기반 (기록 없는 경우, 기본값)**: §3-2E 캘리브레이션 기준으로 CR-10 강도 지시.

### 3-5. 다중 세션 주기화 (팀 모드에 없는, 개인 모드 핵심 기능)

훈련지도서 pp.230~232의 특수성·과부하·점증성 3원칙을 단순화해 적용합니다.

- 세션 간 카테고리/존 강도는 **1단계 이상 연속 상승 금지** (2-5의 팀 모드 규칙과 동일 원칙, 개인은 자동 적용).
- N회 세션마다(예: 4회) 강도를 낮추는 회복 세션을 자동 삽입(점증성 원칙의 디로드).
- 목표 대회 날짜가 있으면 그 날짜까지 역산해 "지금은 EN 위주 구간인지 SP 위주 구간인지"를 자동 배정 — 이 로직은 별도 하위 설계가 필요하므로 이 문서에서는 원칙만 명시하고 상세 계산식은 다음 설계 문서로 분리합니다.

### 3-6. 출력 스키마 (신규 제안 — 팀 모드와 무관, 자유롭게 설계 가능)

```json
{
  "plan_context": {
    "phase": "EN_BASE | SP_BUILD | TAPER | RECOVERY",
    "note": "이번 세션이 전체 계획에서 어떤 위치인지 한 문장"
  },
  "session_summary": {
    "focus_point": "string",
    "total_distance_m": "int",
    "total_min": "int"
  },
  "program": {
    "pre_set":  [{"title": "string", "set": "int", "distance_m": "int", "duration_min": "int",
                  "target_pace_sec": "int|null", "rpe_target": "int(0-10)",
                  "detail": "string", "effect": "string"}],
    "main_set": [ "...동일 구조..." ],
    "post_set": [ "...동일 구조..." ]
  },
  "next_session_hint": "다음 세션 방향 한 문장",
  "feedback_request": ["오늘 세션 완료했나요?", "체감 강도는 몇 점이었나요(0-10)?"]
}
```

팀 모드 스키마와 필드명은 최대한 맞추되(`title`/`set`/`distance_m`/`duration_min`/`detail`), 개인 모드는 계약 제약이 없으므로 `target_pace_sec`·`rpe_target`·`effect`·`plan_context`·`next_session_hint`·`feedback_request`를 자유롭게 추가합니다.

### 3-7. 피드백 루프

세션 종료 후 `feedback_request`에 대한 답(완료 여부, 체감 RPE)을 다음 세션 생성 시 입력으로 사용합니다. 체감 RPE가 계획보다 훨씬 높았으면 다음 세션 강도를 자동으로 한 단계 낮추고, 낮았으면 계획대로 진행 — 이 조정 폭도 §3-5의 "1단계 이상 연속 상승 금지" 규칙 안에서 이뤄져야 합니다.

|---|---|---|

| 피드백 루프 | 없음 | 있음(세션 후 RPE·완료 수집) |

## 6. 강사 검수·미해결 항목 (★)

- ★ §1-4 RPE 치환(CR-10) — 원문 6~10 표현을 임의로 0~10에 매핑한 것. 강사 검수 필요.
- ★ §1-5 레벨×카테고리 게이팅 매트릭스 — 특히 ADVANCED에 SP1까지 허용한 경계선은 추정치. 강사 검수 필요.
- ★ §3-5 주기화 상세 계산식(대회 날짜 역산 로직)은 이 문서에서 원칙만 정의 — 별도 설계 문서 필요.
- ★ §3-4 HRR/Karvonen 입력 필드는 만들되 웨어러블 연동은 범위 밖 — 언제 붙일지 결정 필요.
- 개인 모드 "프로필 + 프로그램 기록" 저장 구조가 `SCHEMA.md`의 기존 `program` 테이블과 호환되는지 미확인 — 이 문서에서는 확인 안 하고 열어둠. 실제 구현 착수 전 `SCHEMA.md` 대조 필요.
- 승인 후 처리: `PROGRAM_LOGIC.md` §2에 "이 문서로 대체됨" 표시, `HANDOFF.md` §12 F-1·F-2를 §2-4·§2-3 반영 완료로 갱신 — **별도 요청 시에만 진행**(이 문서 작성만으로는 미반영).
